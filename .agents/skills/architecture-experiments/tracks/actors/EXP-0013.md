## Decision Question

Which independently owned RefTime, ProofSize, database, and repeated-load components bind current one-Step Actor throughput, and therefore which physical change should be optimized first?

## Governing Specification

- `Exact sections`: `template/pallets/actors/docs/specification.en.md` → `Active Execution State Geometry`, `One-Step Commit Boundary`, and `One Service Contract`.
- `Preserved invariants`: Strict FIFO, class-neutral service, causal next-block readiness, one-Step atomicity, exact Weight ownership, bounded work, and no cold unreached-body proof.
- `Reopen trigger`: Only a semantic defect or infeasibility beyond relevant physical designs; a costly implementation path is not a semantic defect.

## Context and Hypothesis

- `Current architecture`: FIFO probing, paged-head consumption, and execution each reach canonical Actor partitions. The monolithic `ActorContract` maximum is 8,735 bytes, while scheduler execution benchmarks report combined per-Actor models.
- `Reason`: EXP-0001 measured only 32.24–40.99 completed cheap cycles/block against the 100-Step target. Building body geometries before identifying the binding resource risks optimizing a non-binding dimension.
- `Hypothesis`: Repeated canonical-state loading and monolithic Contract decoding materially contribute to one-Step RefTime/ProofSize; queue mutation and Step orchestration may independently bind.
- `Materiality`: Exact reads/writes and ProofSize deltas are material. RefTime attribution is material above `max(2%, 3 × pooled relative model standard error)`. The first implementation target must address the largest causally isolated conforming component, not merely the easiest benchmark.

## Controls

- `Controlled variables`: One cheap one-Step Contract, Actor state, queue page position, runtime limits, production Weight owners, toolchain, database/cache mode, and semantic postconditions.
- `Changed variables`: B1 reloads canonical identity/hot/C6 Contract/funding/run/admission owners during plan preparation and reloads the complete current-Step plan at commit. R1 returns the admission certificate with the first canonical load, constructs the plan from that decoded state, and carries it into the transaction; paged head consumption remains the commit-time ticket/topology revalidation.
- `Confounders`: FRAME storage annotations report unchanged distinct keys even when R1 removes repeated logical loading; therefore RefTime is the binding comparison and unchanged ProofSize/reads are not evidence of no benefit.

## Benchmark Class, Workloads, and Criteria

- `Benchmark class`: Production-Wasm FRAME microbenchmarks plus one unchanged end-to-end FIFO one-Step benchmark.
- `Workloads`: One ready StopCycle Actor at preserved-page and deleted-page boundaries; one Transfer control with effect Weight reported separately; warm repeated populations for end-to-end coefficient stability.
- `Metrics`: Component-wise RefTime/ProofSize, standard error, reads/writes, loaded partition/fragment count, encoded bytes, and end-to-end coefficient.
- `Statistical method`: 50 steps and 20 repeats with no removed samples; independently measured components must reconcile against end-to-end within the declared overlap model.
- `Acceptance criteria`: Every isolated owner has identical semantic postconditions; overlap is explicit; the largest material causal owner is identified; the proposed first optimization addresses that owner without weakening invariants.
- `Rejection criteria`: Non-matching Wasm/source, additive treatment of overlapping models, hidden effect Weight, or inability to preserve identical state/postconditions.

### Post-Acceptance Loaded Placement and Persistence Correction

The direct P32 maximum-geometry fresh-Opening progress owner exposed two residual reloads after R1: successor placement reconstructed service state, and run persistence reloaded identity, hot state, admission, and the next tail fragment despite carrying a fully reconstructed execution view inside the same atomic attempt. Production now patches the post-Step placement view from the canonical hot owner, reuses that hot owner for queue preflight, and persists the already validated run against the transaction-revalidated FIFO ticket and immutable loaded Contract authority.

The focused 50-step/20-repeat maximum-geometry model changed from transient v3 output `4fcc1207` to R2 output `47862f4a`:

| Model | RefTime | Estimated ProofSize | Reads | Writes |
| --- | ---: | ---: | ---: | ---: |
| v3 loaded placement, reload persistence | `218,607,089 + 135,052,469t` | `8,998 + 21,386t` | `15 + 16t` | 8 |
| R2 loaded placement and persistence | `178,698,884 + 127,790,332t` | `7,833 + 21,350t` | `13 + 16t` | 8 |

At P32 `t = 8`, R2 changes RefTime `1,299,026,841 → 1,201,021,540` (`-7.54%`), ProofSize `180,086 → 178,633` (`-0.81%`), and reads `143 → 141`, with writes unchanged. The v3 matching Wasm was not retained, so this is strong focused implementation-correction evidence rather than a new controlled architecture decision. R1 remains the accepted causal decision; R2 narrows its reuse boundary without changing semantic ownership.

The fresh-Opening completion benchmark then exposed a second equivalent reconstruction: ordinary non-closing completion reloaded the full Active Contract only to test close policy already present in the loaded execution view. Before correction, the minimal owner was `100,420,049 + 6,883,407t` RefTime, `6,370 + 2,669t` ProofSize, `6 + t` reads, and three writes. Selecting the close condition from loaded immutable policy and reloading complete Active state only when a close is actually selected changed the model to `69,687,645 + 524,747t` RefTime, fixed `5,696` ProofSize, three reads, and three writes. At P32 `t = 8`, this is `155,487,305 → 73,885,621` RefTime (`-52.48%`), `27,722 → 5,696` ProofSize (`-79.45%`), and `14 → 3` reads. A separate maximum-realizable completion owner preserves dependency reads without charging them to the minimal path.

Fresh-Opening retry exposed the same pattern in wakeup placement. The first direct minimal owner still reloaded current-Step service state through the wakeup helper and measured `150,819,172 + 892,814t` RefTime, `6,476 + 24t` ProofSize, ten reads, and eight writes. Passing the transaction-loaded hot authority through successor scheduling changed the model to `105,824,662 + 467,902t` RefTime, `5,359 + 24t` ProofSize, seven reads, and eight writes. At P32 `t = 8`, this is `157,961,684 → 109,567,878` RefTime (`-30.64%`), `6,668 → 5,551` ProofSize (`-16.75%`), and `10 → 7` reads. The maximum-realizable retry owner remains branch-local at `1,098,763,101` RefTime, `177,918` ProofSize, 137 reads, and eight writes for P32; its dependency reads do not tax the minimal path.

Fresh-Opening non-closing failure uses a pre-effect invalid split to isolate control work from Task effect Weight. The minimal owner is `61,705,088 + 152,378t` RefTime with fixed `5,633` ProofSize and `3/3` reads/writes; at P32 this is `62,924,112`. The maximum-realizable owner is `102,259,467 + 118,565,318t` RefTime, `7,160 + 21,381t` ProofSize, `6 + 16t` reads, and three writes; at P32 this is `1,050,782,011` RefTime, `178,208` ProofSize, 134 reads, and three writes. Separating these branches prevents Opening dependency work from becoming a failure-path ceiling tax.

Terminal-close assurance showed that `finalize_actor` redundantly reconstructed the same Active Contract immediately after execution had obtained exact current close authority. A loaded finalizer changed the minimal P32 full-branch RefTime `283,813,297 → 244,982,247` (`-13.68%`) while estimated ProofSize and storage keys remained effectively unchanged at `28,329`, 21 reads, and 20 writes. Maximum-realizable P32 close is `1,405,800,875` RefTime, `185,618` ProofSize, 152 reads, and 20 writes. These full-branch models are assurance, not Step control owners: scheduler admission already reserves `close_actor` separately, terminal cleanup charges no Actors fee, and the logical completed/failed outcome selects its direct Step owner. Substituting the full close model as actual control would double-reserve cleanup and violate fee ownership.

## Derived Metrics

- Historical D1 attribution remains non-additive: standalone state probe was 35.55% and cycle orchestration 48.64% of its then-current marginal coefficient.
- Against exact B1, R1 reduces the end-to-end marginal RefTime coefficient by `29,940,217`, or `17.87%`, and the constant by `28,077,000`, or `16.00%`.
- R1 leaves measured/estimated ProofSize models and generated distinct-key read/write counts unchanged. It is a RefTime-only Pareto improvement with no measured component regression.
- B1 pooled coefficient standard error is approximately `217,930`; the measured marginal delta is more than 137 times that error and far above the predeclared 2% floor.
- Unchanged key counts confirm that the win comes from decoded loaded-state reuse and removal of repeated logical access rather than a storage-ownership or proof contract change.

## Statistical / Variance Notes

Historical D1 used one matching benchmark Wasm. The controlled B1/R1 pair used separate exact source-bound Wasm artifacts because the changed production path necessarily changes Wasm, with identical toolchain, runtime constants, benchmark command, 50 steps, 20 repeats, cache 1,024, state setup, and semantic postconditions. B1 slope standard error is `145,483`; R1 is `162,214`; no samples were removed.

## Result

Historical D1 narrowed the target without causal attribution. The exact controlled B1/R1 pair now establishes that carrying one decoded canonical state and admission certificate through ticket construction, current-Step planning, admission, FIFO consumption, and execution reduces the cheap-Step marginal from `167,553,076` to `137,612,859` RefTime (`17.87%`). ProofSize remains `3,154` estimated per Actor and generated storage counts remain six reads/three writes per Actor.

## Interpretation

- `Supported`: Repeated canonical decoding/loading in the converged scheduler was a material RefTime owner; R1 removes that overlap without changing semantic state, storage keys, ProofSize, FIFO order, or writes.
- `Not supported`: Generated read counts cannot reveal repeated logical loading, and the result does not prove full C6 body reconstruction is optimal or that other standalone Weight owners are additive.
- `Residual`: Scheduler still reconstructs the bounded full C6 Contract before building the current-Step plan. EXP-0016 hot-header/current-fragment conversion remains the next distinct mechanism rather than part of this accepted reuse decision.

## Decision

Accept R1 as the production loaded-state reuse baseline. Its `17.87%` marginal RefTime reduction is material, component-wise non-regressing, and preserves identical one-Step semantics and storage ownership. Keep one canonical loaded-state/admission result through planning and execution; do not restore independent plan or commit-time Contract reloads. FIFO head consumption remains the atomic ticket/topology revalidation immediately before effect execution.

## Validity

- `Establishes`: Exact B1/R1 source and Wasm identities, a `17.87%` marginal RefTime win, unchanged ProofSize/storage-key models, identical semantic postconditions, and R1 as the selected production reuse topology.
- `Does not establish`: Additive owner attribution, the benefit of replacing full Contract reconstruction with hot-header/current-fragment classification, 32-Step dispatchability, or external-operation overhead.
- `Later topology`: The subsequent EXP-0016 hot-head/current-fragment service conversion retains R1 and measured `135,919,720` marginal RefTime in its focused run. The R2 implementation correction extends loaded-state reuse through successor placement and run persistence. Both supersede earlier production Weight/Wasm handoff identities, not the causal B1/R1 decision.
- `Invalidation triggers`: Removal of loaded-state reuse, a changed semantic workload, canonical owner replacement that defeats the reuse boundary, runtime limits, toolchain, or production-Wasm method changes.

## Architecture Impact

R1 is production architecture: scheduler service reuses the canonical state and admission certificate already loaded for classification to construct one `CurrentStepPlanOf<T>`, then carries that plan across admission into the atomic FIFO-consume/execution transaction. R2 extends that same authority through successor placement and run persistence while FIFO head consumption remains the atomic ticket/topology revalidation. The implementation architecture may cite this record after full Weight and validation converge.
