## Decision Question

Does the retained `task_split_transfer(legs)` coefficient bound every reachable four-leg SplitTransfer effect, including maximum-header User recipients, inline recipient expiry and the native staking-liquidity bridge?

## Context and Candidates

- `Current architecture`: Runtime admission and invoked settlement both select `task_split_transfer(legs.len())` regardless of recipient class, expiry or native side effects; no separate terminal-effect charge exists. `TmctolAssetOps::transfer` performs ingress preflight/notification and balance-dependency publication per leg inside the invoking Task.
- `Hypothesis`: The retained owner, benchmarked with distinct active System recipients, bounds every reachable recipient mix.
- `Materiality`: One reachable selected effect above the owner in either dimension rejects it as complete.
- `Controlled / changed variables`: One benchmark-only wrapper invokes the exact `execute_prepared_task` SplitTransfer body for every profile (balance check, all-leg preflight, Task event, transaction), leaving Step control to its own owner; only recipient geometry changes.

## Result

U exceeds the retained four-leg projection in both dimensions. E exceeds H by about 1,000 ProofSize and roughly 2.1 G RefTime base, so one inline expiry costs more than a healthy User recipient. C stays below the retained two-leg projection. A four-recipient runtime regression proves the terminal branch is live: the mandatory Prepass admits Service and at least one same-window expired User recipient closes after its own ledger transfer within the sender's Service turn; other recipient closures do not establish a simultaneous-close maximum.

## Interpretation

The generated benchmark already sends every leg to a distinct active System recipient with a saturated AddressEvent source filter and certified ingress; the underbound comes from User recipients' larger headers and synchronous certified-ingress finalization (`preflight_funding_event` admits `WindowExpired`, then `apply_address_event_parts` finalizes the Actor). The complete selector must therefore include inline terminal finalization. Isolated ProofSize witnesses must not be summed into a four-close lower bound.

- `Native bridge`: In production `TrustedSet` (fixed by `RuntimeNativeSecurityModeProvider` outside `runtime-benchmarks`), the Fee Sink two-leg Native SplitTransfer takes the staking-liquidity bridge — Native transfer, slash and local staking-asset mint, then certified ingress. Staking denies security-reward funding in that mode, so the LP-backed three-leg success path is not a production Fee Sink effect; keep its fail-closed preflight. `task_transfer`, `task_mint` and `task_split_transfer` do not bound the extra `Balances::slash` plus local asset-ID-0 `pallet-assets::mint_into` with an active liquidity recipient, and adding whole Task weights would double-count movement and notification. C measures only the isolated pool/bridge branch from a non-Fee-Sink source.
- `Failure selector`: Source-balance refusal; last-leg preflight refusal before mutation; or later transfer or certified-ingress rejection after earlier legs executed, rolling back the whole Task. Every invoked attempt settles the same reservation; rollback without lasting custody is not zero work. `fee_sink_actor_splits_trusted_set_native_flow_to_staking_and_lp_ingress` proves a reachable late failure: with the native staking asset frozen, the first leg executes and the second bridge mint fails `AssetNotLive`, rolling back both.
- `Admission`: `contract_steps_admission_weight_upper()` composes selected maximum Step control plus effect, admission overhead and cleanup; `running_inner_fixture_admission_frontier_is_class_neutral` fits selected geometries without double-counting the effect. Neither is universal maximum-Step evidence.

## Decision

Rejected: the retained `task_split_transfer` owner is not a complete four-leg bound (O1, O2); O3 is Inconclusive and certifies nothing. Outcome class: research result. Stop adding Task × recipient profiles; O4 closes only through one conservative component-wise selector covering positive, inline-terminal, bridge and failure branches, proven against Actor base, Control and Service independently.

## Validity

- `Establishes`: Concrete underbounds for maximum-header User and inline-expiry recipients; live reachability of inline terminal close and late failure.
- `Does not establish`: A universal recipient, terminal or failure maximum; a production coefficient; the full Fee Sink Step.
- `Invalidation triggers`: Leg cap, header limits, ingress finalization, native bridge path or security mode changes.
