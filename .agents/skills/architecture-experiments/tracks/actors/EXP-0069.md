## Decision Question

Does one complete consumed-source User Opening completion owner cover the admitted FundingSourcePolicy header-width envelope, from `OwnerOnly` through maximum `SignedAllowlist`, without changing public context or duplicating outer FIFO, Pipeline, Action, or hold ownership?

## Governing Specification

- `Header and funding semantics`: `template/pallets/actors/docs/specification.en.md` §§3.1, 3.4, 3.5 and 7.3–7.7.
- `Resource ownership`: `docs/actors-resource-policy.specification.en.md` §§1, 4–6 requires complete component-wise admission and actual settlement with one owner per cost.
- `Invariant`: Preserve C1, class-neutral FIFO, immutable cutoff, Q1, causal floor, custody, independent Pipeline/Action fees and committed-Step durability.
- `Reopen trigger`: A semantic need to distinguish funding policies belongs to the specification; measured byte or Weight growth alone does not authorize a context/API/storage change.

## Context and Hypothesis

- `Current evidence`: EXP-0067's legal native witness gives `OwnerOnly` versus maximum 16-source `SignedAllowlist` header sizes 157/670 bytes while both produce context `[0,1,0,0,0,0,40]` and stored Control `2,810,763,536 / 33,863`.
- `Accepted input`: EXP-0068 accepts separate zero-tail and positive-tail User completion inner models only for its attained minimal-head fixtures; it does not qualify arbitrary Contract heads.
- `Hypothesis`: A maximum admitted FundingSourcePolicy benchmark at the same consumed-source completion boundary can provide a conservative inclusive header envelope while retaining the existing scalar selector. If it cannot, EXP-0067 must choose the smallest source-owned distinction proven necessary.
- `Materiality`: Coverage and containment, not a percentage speedup. One reproducible wider-header path outside the selected envelope falsifies qualification.

## Result

Measured and interpreted. H0/H16 execute successfully on one fresh benchmark Wasm. H16 retains identical generated I/O, adds exactly the independently observed 513 proof bytes and component-wise dominates H0. Production Weight, production Wasm and runtime binding remain unchanged.

## Interpretation

The wider legal header is not an unmodelled branch after measuring H16: its tracked I/O is identical and its generated ProofSize grows by the exact 513-byte policy width. H16 is therefore the sound reference-binding maximum for this isolated zero-tail FundingSourcePolicy axis. This does not qualify other optional Contract-head fields or positive-tail hold release. The existing scalar context may select the inclusive H16 owner; richer public context is not earned by this evidence.

## Decision

Accepted for the reference `MaxWhitelistSize = 16` FundingSourcePolicy axis. Select H16 `893,949,000 / 7,990` as the complete inclusive zero-tail User completion inner input for EXP-0067. Retain EXP-0068's accepted positive-tail owner independently. Do not install either coefficient until EXP-0067 proves non-overlapping live selection and component-wise maximum/actual containment.

## Validity

- `Establishes`: Same-Wasm H0/H16 reference evidence, exact fee/hold postconditions, exact tracked-I/O coverage and an inclusive zero-tail FundingSourcePolicy maximum for `MaxWhitelistSize = 16`.
- `Does not establish`: Production selector correctness, arbitrary optional Contract-head coverage, positive-tail or combined maximum-header/positive-tail coverage, generic-host maxima or release acceptance.

- `Invalidation triggers`: Funding policy encoding/admission, User completion body, Pipeline collection, hold reconciliation, benchmark method, `MaxWhitelistSize` or toolchain change.
- `Residual qualitative insight`: Scalar selection can remain sound when its inclusive owner is proven; equal contexts alone do not prove that owner.
