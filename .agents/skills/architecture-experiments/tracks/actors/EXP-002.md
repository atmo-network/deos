## Decision Question

Should the canonical semantic mutation owner omit a Put whose fully validated replacement equals freshly loaded current state, without removing a read, changing authority or crossing an effect/fee callback boundary?

## Context and Candidates

- `Current architecture`: `mutate_actor_semantic_state` freshly Gets the complete bounded record, validates Publish/Replace/Remove through `apply_actor_semantic_mutation`, then always submits the resulting Put/Delete. Placement and Run may change while this record remains identical.
- `Hypothesis`: Equality-gating only the final storage submission removes the observed redundant semantic Put without changing any validation or semantic result. This does not reopen EXP-001's process, residence, round, lifecycle or layout decisions.
- `Materiality`: Remove the one unchanged 351-byte semantic Put in H1 length 12/block 4, with unchanged Gets, roots, fees, outcomes and ordered service. Reject any new logical operation or semantic regression. No CPU/PoV/throughput threshold is claimed.
- `Controlled / changed variables`: Frozen B28-core workload, harness, budgets, prices, host/toolchain and observer; change only storage submission after validation. A bounded record equality comparison is additional CPU work and its timing is unmeasured. Candidate set is exactly baseline A and candidate B.

## Workloads and Criteria

- `Evidence class`: Native property/regression tests and matched SDK logical-state-event H1 comparison. No physical timing measurement.
- `Acceptance criteria`: Fresh read and complete expected-value validation remain before elision; changed Publish/Replace/Remove persist normally; stale/missing/republication fail identically; rollback restores state. H1 roots, economic/fee/Weight traces and geometry match exactly. At least the named Put disappears with no added Gets or other operations.
- `Rejection criteria`: Any stale no-op accepted, changed mutation lost, root/fee/order/custody mismatch, added logical access, or failure to remove the named write. Retained Weight is held fixed, not regenerated to manufacture an improvement.

## Result

O1 and O2 pass. Valid no-op results, changed writes, Publish/Remove, missing/stale/republication refusal and outer rollback retain behavior. Both stale-equal shapes fail: expected equals replacement but storage changed, and replacement equals storage but expected is stale. The complete H1 A/B differs only by the predicted semantic submission elisions. Default/full-local and scoped production-artifact checks pass; the broad all-features test timeout remains an explicit incomplete validation.

## Interpretation

B is strictly better in the measured logical-submission dimension and equal in every other measured workflow/access dimension: 18 singleton Puts and 6318 submitted value bytes disappear, while the independent heavy refusal scaffold accounts for 416 additional omissions. The fresh record is already decoded in A and B; B adds only bounded RAM equality, not an extra decode/read or proof access. Its CPU effect is unmeasured, so this is not a demonstrated physical Pareto improvement, lower tariff, shorter block or capacity gain. Keeping generated prices fixed prevents confusing code elision with repricing. The all-features timeout limits broad validation, not the observed A/B identity or focused callback/rollback partition.

## Decision

Select and retain B after Result → Interpretation. Decision scope: equality-gated semantic submission with native correctness, matched finite H1 truth and scoped current-production-Wasm regressions. Outcome class: efficiency improvement restricted to logical storage submission. Stop at the frozen O1/O2 success; no new layout, cache, read reuse or candidate is admitted. Keep Weight/config and fees fixed. O3 elapsed timing is Inconclusive; broader proof/CPU, all-features completion and release acceptance remain unproved, not implied by this selection.

## Validity

- `Establishes`: Validated equal semantic replacements omit their Put without losing fresh expected-value checks, changed mutation, rollback or any of the observed finite H1 outcomes.
- `Does not establish`: Global caller/host maxima, full runtime/all-features/release acceptance, CPU/backend-I/O/proof/throughput improvements or lower tariffs.
- `Invalidation triggers`: Any change to controlled source/workload/price/observer inputs or proof that equal values have a separately observable storage-submission contract.
