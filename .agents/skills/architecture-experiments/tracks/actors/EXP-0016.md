## Decision Question

Does a hot Contract header that uniquely owns Step 0 and stores only Steps 1..N in lazy tail fragments preserve the one-read one-Step path while satisfying no-ceiling-tax, later-cursor loading, bounded lifecycle, exact reconstruction, and production dispatchability better than monolithic B0?

## Governing Specification

- `Exact sections`: `template/pallets/actors/docs/specification.en.md` → `Hot/Cold Physical Contract`, `Complete Projection`, `One-Step Commit Boundary`, and `Active Execution State Geometry`.
- `Preserved invariants`: One semantic ordered Contract; no duplicate authored Step owner; exact semantic/body commitments; activation without tail reads; execution loads only header plus the current tail fragment when cursor is nonzero; atomic lifecycle; stale authority fails closed; bounded reconstruction; no ceiling tax.
- `Reopen trigger`: Only demonstrated semantic defect or infeasibility beyond relevant physical designs. Candidate performance failure rejects the candidate, not the specification.

## Context and Hypothesis

- `Evidence`: EXP-0003 rejected one-cell C1 because header-plus-cell loading added a read and C1 lost every 1..=8 lifecycle/current-load/reconstruction branch while increasing retained bytes 14.46× at one Step and 21.79× at eight Steps.
- `Design pressure`: The release target is 100 completed one-Step Actor Steps/block, while the accepted 32-Step ceiling forbids monolithic maximum-body proof on short Contracts.
- `Hypothesis`: Uniquely inlining Step 0 removes C1's extra one-Step read and tail record. Lazy tail authority preserves ceiling independence for short Contracts and bounds later-cursor reads.
- `Materiality`: Reads/writes, ProofSize, loaded fragments, encoded bytes, and correctness are exact. RefTime uses `max(2%, 3 × pooled relative model standard error)`. The winner must improve the binding one-Step path without exceeding predeclared lifecycle/dispatchability bounds.

## Benchmark Class, Workloads, and Criteria

- `Benchmark class`: Matching production benchmark-Wasm storage/lifecycle/current-loader/reconstruction comparisons plus deterministic retained-state profile and semantic fault tests.
- `Workloads`: One-Step Contract; maximum current 8-Step Contract; Step 0 load; first/middle/last tail load; create/update/close; full reconstruction; missing/stale/wrong-actor/wrong-index tail authority.
- `Metrics`: Component-wise RefTime/ProofSize; reads/writes; encoded persistent bytes; loaded fragments; maximum call dispatch fit; exact semantic/body equality; Wasm size.
- `Statistical method`: 50 steps, 20 repeats, no sample removal, one matching Wasm per controlled matrix.
- `Acceptance criteria`: One-Step current load uses one storage read, no tail record, and no higher estimated ProofSize or material RefTime than matched B0; tail current load is bounded independently of global ceiling; exact reconstruction/fault tests pass; persistent growth is linear only in authored tail Steps; and the conservative sum of existing full lifecycle Weight plus C5 micro-storage Weight remains inside each production dispatch envelope component-wise before production integration.
- `Rejection criteria`: Extra one-Step read/tail state, maximum-ceiling proof on one-Step Contracts, duplicate authored Step ownership, stale fragment acceptance, unbounded cleanup, non-dispatchable lifecycle, or a material one-Step regression without a release-target benefit.

## Derived Metrics

C5 Step-0 load improves RefTime by `9.33%`, reduces estimated ProofSize by 6 bytes, retains one read, and creates no tail record. At `n=8`, C5 changes RefTime versus B0 by create `+311.20%`, update `+302.70%`, close `+76.40%`, reconstruction `+198.80%`, and tail load `+37.92%`. C5 retained bytes increase by `+761.54%` at one Step and `+1,855.88%` at eight Steps. C5 tail load adds one read.

At `n=8`, C6 changes RefTime versus matching B0 by create `+119.27%`, close `+17.43%`, reconstruction `+84.97%`, and tail load `+38.68%`. Versus C5, C6 reduces retained bytes `56.84%`, create RefTime `46.56%`, close `33.54%`, and reconstruction `39.20%`; its tail-load RefTime differs by less than the 2% materiality floor. C6 preserves C5's measured Step-0 result because the head is byte-identical and no tail key exists for one-Step Contracts.

## Statistical / Variance Notes

Both valid matrices used 50 steps and 20 repeats with no sample removal and one matching Wasm per matrix. Generated RefTime slope errors remain below the 2% materiality floor. C6 tail-load differs from C5 by less than that floor. Chunk-count step functions make generated linear DB/proof coefficients non-authoritative; exact raw maximum key counts, encoded bytes, and measured RefTime remain valid. No outlier was removed.

## Result

C6 preserves the accepted one-read, no-tail one-Step path and materially dominates C5 in lifecycle RefTime and retained bytes without a material tail-load RefTime loss. C6 still costs more than monolithic B0 on tail-sensitive paths, but B0 fails the 32-Step no-ceiling-tax direction that motivated body separation. Four-Step chunks bound later-cursor decoding independently of the global ceiling and reduce the 32-Step tail-key ceiling from 31 C5 cells to eight chunks.

## Interpretation

The Pareto comparison selects C6 among conforming candidates. B0 remains faster and smaller at the current eight-Step profile but cannot satisfy the accepted scalable physical contract without loading the whole body. C5 proves inline Step 0 but repeats authority and trie work per Step. C6 retains the binding one-Step improvement while sharply reducing C5's cardinality costs. A two-Step candidate is not earned because it would increase keys and authority repetition while C6 introduces no material tail-load RefTime regression against C5. An unbounded tail remains non-conforming because its decode/proof exposure grows with the global ceiling.

## Decision

Accepted. C6 is the selected I2 production geometry: one uniquely owned inline Step 0 and authority-bound contiguous tail chunks of at most four Steps. Experiment-named stores/functions and rejected C5 code have been removed. Production implementation must parameterize Weight by exact chunk count or charge worst-case constants and validate lifecycle/current-Step behavior before architecture documentation changes.
