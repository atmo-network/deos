## Decision Question

Does a selected complete two-User maximum funded/watch-header late-fee pair→scalar fallback fit the retained `crossing_placed_pair_unit` reservation `12,577,613,000 / 162,782` including RocksDB costs? EXP-0156's ordinary-header rollback witness fitted this bound, but one independent header-width input remains in the live pair-only failure selector. This test is a falsifier, not a universal maximum certificate.

## Governing Specification

- `Exact section`: `docs/actors-resource-policy.specification.en.md` §4; `template/pallets/actors/docs/specification.en.md` ObservationCrossing Trigger fee, maximum-before-mutation and rollback.
- `Invariant`: A failed pair attempt rolls back the already attempted first fee and source movements, then retries scalar while charging physical work once through its admitted Actor Control branch; exactly one fee commits.
- `Reopen trigger`: The complete charged pair owner cannot contain its physical late-failure path under one-third Actor Control.

## Context and Hypothesis

- `Current architecture`: The pair branch calls `do_crossing_placed_batch_or_single_unit(2)` under a single `crossing_placed_pair_unit` reservation. If the second fee attempt returns `InsufficientFee`, it rolls back the batch and retries the first scalar work unit. EXP-0156 measured this on ordinary User headers; current runtime cannot admit a batch larger than two under its retained exact-third Control cap (package owner and runtime arithmetic tests).
- `Reason`: Canonical User header reads and funding/watch decoding participate in both the unsuccessful pair and scalar retry. One meaningful stricter header width could falsify the successful pair bound despite the earlier ordinary-header non-falsification.
- `Hypothesis`: The selected full-header failure estimate exceeds the current pair reservation in RefTime or ProofSize.
- `Materiality`: Any component excess makes the charge unsafe for that selected path; a fit leaves the complete physical owner gate open.

One selected benchmark estimate falsifies containment under the existing generated ProofSize model, not an actual trie-recorded relay PoV upper. RefTime variance across benchmark Wasm builds is uncalibrated; the present outcome is ProofSize-model-driven.

### Benchmark Evidence Disposition

- `Benchmark Evidence Status`: Qualified — selected generated-estimate ProofSize underbound; observed proof and RefTime do not falsify the retained pair for this fixture.
- `Reassessment Trigger`: Runtime fee collector, header bounds, produced benchmark code, DB pricing, production Weight, or one-third resource policy changes.
- `Compared Observation IDs`: Historical ordinary EXP-0156 `3d2dd4d6…` and initial H1 `f0109e6c…` remain independent. New matched ordinary/full-header extras on `b7a2ac76…` confirm the same `14,007` estimated ProofSize gap without promoting the result to a production maximum.
- `Noise / Stability Evidence`: Original and reissue each use 50×20 min-duration-zero generated fits, no per-repeat distribution. Full-header measured/estimated ProofSize remains `17,399 / 176,789` across two Wasm builds; its base RefTime changes from `2,351,455,000` to `2,340,559,000` without altering the charge decision.
- `Current Authority`: Two full-header runs, including a same-Wasm ordinary control, keep the selected estimate `14,007` above the retained pair's ProofSize model while measured proof remains below charge. Six extra tail-chunk reads have a source owner; production still uses the successful-pair Weight and complete failure/header dominance is unknown.

## Result

The selected two-User maximum funded/watch-header pair→scalar fallback produces a `176,789` generated ProofSize estimate above the charged pair's `162,782`; its `10,101,455,000` RocksDB-inclusive RefTime fits the retained `12,577,613,000`. The measured proof `17,399` fits the charge, so the generated-model and observed-proof claims remain distinct.

## Interpretation

The ordinary-header EXP-0156 non-falsification does not qualify this stricter header domain. Generated estimated ProofSize must be at least sufficient for the selected failure branch if used as the binding model; this one output is not the maximum-header runtime PoV or complete selector maximum. No second useful Trigger fee commits for rollback, and its physical attempt remains in the invoking pair Control owner.

## Decision

Reject the retained successful-pair **estimated ProofSize model** as containing this selected full-header failure estimate. Outcome class: research result; one bounded witness completes this question. Do not hand-edit production Weight/ABI or claim measured PoV underbound; coordinate complete pair-selector generation and mandatory/Service admission first.
