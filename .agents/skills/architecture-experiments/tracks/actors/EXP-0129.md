## Decision Question

What is the smallest status and authority state machine that distinguishes current-state Park from explicit reversible revocation and irreversible retirement, stops execution before bounded detach, preserves custody and committed Cycle effects, and permits only authorized generation-safe revival without stale wake or cleanup authority?

## Governing Specification

- `Exact section`: `BACKLOG.md` N4.1; `template/pallets/actors/docs/specification.en.md` §2.3 and §9; `tests/current_state_semantic_oracle.rs` disablement and stale-retirement witnesses.
- `Invariant`: Only `Serving` may own Live, Sleeping, Parked, or Pending execution residence. `Disabled` owns no executable residence and can return only through explicit typed authority. `Retired` never returns. No transition rolls back a committed Action or changes sovereign custody.
- `Reopen trigger`: A supported control path leaves execution authority after revocation, an ordinary wake changes Disabled/Retired state, revival reuses stale evidence or generation authority, or old cleanup can mutate a replacement.

## Context and Hypothesis

- `Current architecture`: EXP-0128 selects direct revocation before bounded generation-bound cleanup, but does not decide which statuses preserve a resumable semantic basis or which authority may revive them.
- `Reason`: Park is an automatically maintained negative current-state conclusion, not owner intent. Collapsing Park, pause, disablement, deactivation, and retirement either grants wake paths control authority or destroys state needed for honest Mutable revival. Preserving raw old residence is also unsafe because deadlines, revisions, and plans can become stale while service is revoked.
- `Hypothesis`: Keep one process-owned `ServingStatus`: `Serving`, `Disabled(cause, authority, suspended_basis)`, or `Retired(reason, cleanup)`. Revocation linearizes by setting non-serving status before direct detach. Reversible control preserves only the semantic run/retry/failure basis needed to reconstruct service from current state; retirement is irreversible. Revival is a fresh admitted transition under the exact disabling authority and current generation/plan, never a wake.
- `Materiality`: Freeze exact state transitions, interrupted-Cycle disposition, and revival authority. Encoded fields, cleanup page topology, numeric reserve, and runtime implementation remain N4.2/N5.2.

## Measurements

### Canonical Status and Linearization

`Process.status` is the sole serving-authority discriminator:

```text
Serving
Disabled { cause, revival_authority, suspended_basis, cleanup }
Retired { reason, generation, cleanup }
```

Live, Sleeping, Parked, and Pending are residences only while status is `Serving`. `Parked` means the runtime has a complete current negative certificate and return plan; it is never an owner/protocol status. `Disabled` is reversible only when its typed cause declares an explicit revival transition. `Retired` is irreversible process authority: only bounded cleanup and final deletion remain.

A revocation transaction validates caller/protocol authority, exact generation, status, direct residence handle, Cycle boundary, and complete immediate resource envelope. It then sets `Process.status` non-serving, so every carrier validation and callback fails closed; directly detaches executable residence; records any bounded cleanup cursor; and commits together. Callback failure or late validation rolls back status and detach. Once status is non-serving, a stale ring, deadline, Park registration, Pending reference, or callback has no execution authority even before its physical cleanup.

### Revocation and Cycle Matrix

| Transition | Cycle disposition | Preserved basis | Resulting status |
| --- | --- | --- | --- |
| Owner pause | Do not undo committed Steps; freeze Running/Suspended semantic cursor | Contract/plan generation, run cursor, committed counters, retry attempt/deadline/failure streak, terminal horizon | `Disabled(OwnerPaused, owner, basis)` |
| Owner resume | No old residence restored blindly; classify basis against current block/time/state | Running continues at exact next Step or retry boundary; Idle performs a fresh current start check | `Serving` plus one newly admitted Live/Sleep/Pending/Park residence |
| Owner run cancel | Cancel only uncommitted suffix; committed prefix and fees remain final | Idle Contract plus current failure/terminal state required by contract | `Serving`; fresh current start classification no earlier than B + 1 |
| Owner deactivate | Cancel uncommitted run suffix and revoke the active process | Persistent identity/custody/control nonce and Contract only where lifecycle contract retains it | `Disabled(OwnerDeactivated, owner, dormant basis)` |
| Owner reactivate | Admit a fresh process generation/plan and current-state check | Identity/custody persist; no old run, retry, Park certificate, or acknowledgment transfers | New `Serving` generation, B + 1 eligible |
| Contract update | Retire old executable meaning before replacement can serve | Committed economic effects/custody; replacement gets distinct generation namespace | Old `Retired(UpdateReplaced)` cleanup plus atomically admitted new generation, or unchanged old state on refusal |
| Protocol disable | Revoke under named protocol authority and reason | Cause-defined semantic basis; no implicit owner override | `Disabled(Protocol(reason), authority, basis)` when reversible |
| Mandatory terminal/close | Cancel uncommitted suffix and permanently revoke | Custody only; committed effects remain final | `Retired(reason)` until complete cleanup/deletion |

Pause is not economic rollback or time freeze. Deadlines and source revisions continue monotonically while disabled. The suspended basis preserves retry attempt count and earliest retry boundary; resume uses `max(current, retained deadline)` and cannot erase a backoff. A terminal condition whose owner is allowed to run while disabled takes precedence and retires the process; owner resume cannot repair an irreversible or window-expired terminal result.

### Authorized Revival Protocol

A revival transaction must:

1. Match Actor id, current process generation, `Disabled` cause, and exact `revival_authority`; `Retired` has no matching transition.
2. Reject Immutable actor-scoped mutation. System authority is exactly its configured owner or `SystemOrigin` where the governing lifecycle contract already grants it; status does not manufacture a new authority.
3. Revalidate retained Contract/plan bindings, current terminal predicates, current source revisions/time, admission capacity, economic holds/fees, complete residence transfer, and cleanup compatibility.
4. Derive one destination from current truth. A retained Running cursor may become Live or Sleeping at its unchanged Step/retry boundary. Idle/deactivated revival begins a fresh current check and cannot reuse an old Park certificate or acknowledged revision.
5. Stage the destination under non-serving status, replace status with `Serving` as the sole linearization point, bind the exact generation, mark admission in B as considered and eligible from B + 1, and commit all writes together.

Destination or resource refusal leaves `Disabled`, its suspended basis, cleanup cursor, revisions, and retry history unchanged. There is no partially serving state and no fallback queue. Ordinary balance/observation invalidation, deadline extraction, Manual hint, cadence, stale cleanup, or service traversal observes non-serving status and may perform bounded stale detach only; it cannot invoke revival.

### Status Transition Matrix

| From | Event | To | Authority |
| --- | --- | --- | --- |
| Serving Parked | dependency invalidation/review | Serving Pending | Ordinary source authority; not revival |
| Serving any residence | owner pause | Disabled OwnerPaused | Mutable User owner only |
| Disabled OwnerPaused | owner resume | Serving reconstructed residence | Same authorized Mutable owner |
| Serving any residence | owner deactivate | Disabled OwnerDeactivated | Mutable User owner only |
| Disabled OwnerDeactivated | owner reactivate | New Serving generation | Same authorized Mutable owner plus fresh admission |
| Serving/Disabled | compatible protocol disable | Disabled Protocol(reason) | Named protocol authority only |
| Disabled Protocol(reason) | protocol re-enable | Serving reconstructed residence | Exact authority declared by that reason |
| Serving/Disabled | terminal/close/retire | Retired | Owning terminal or authorized close transition |
| Retired | wake/resume/reactivate/update | Retired | No authority; reject/no-op as appropriate |
| Old Disabled/Retired cleanup | current generation exists | Current generation unchanged | Cleanup can detach exact old-generation handles only |

`Immutable` has no owner pause, resume, deactivate, reactivate, cancel, update, or close edge. Mandatory authored/temporal terminal and insufficient-admission apoptosis remain independently effective. `System` actor-scoped rights remain exactly those already configured; protocol disable/re-enable must name its authority and cannot be inferred from class alone.

### Full Capacity, Cleanup, and Precedence

Revocation uses EXP-0128 direct unlink and the mandatory Control envelope, not an ordinary destination. Therefore full Live/Sleep/Park/Pending carriers cannot prevent status from becoming non-serving. If detach cannot finish in the immediate bounded unit, `Disabled.cleanup` or `Retired.cleanup` retains exact generation/phase/handle authority. Cleanup never changes suspended semantics and cannot revive.

Precedence for one admitted control is:

1. Exact identity/generation and authority;
2. Already Retired or mandatory terminal that cannot be repaired;
3. Existing compatible status/no-op classification;
4. Complete immediate revocation/revival/update admission;
5. One transactional status/residence commit.

A window-expired or irreversible terminal condition substitutes retirement before requested revival/update. A repairable non-window terminal may be changed only by a control already authorized by the lifecycle contract and only before retirement commits. Concurrent stale work loses on generation/status validation.

## Result

Candidate A supplies one explicit serving-authority discriminator. Revocation removes authority before physical detach, reversible disablement preserves only the exact semantic basis needed for honest reconstruction, and revival is a fresh authorized current-state transition. Park remains automatic negative evidence; Retired remains cleanup-only. Every committed Action and custody balance survives lifecycle control unchanged.

## Interpretation

Reversibility belongs to a typed authority transition, not to absence from a queue. This avoids two symmetric errors: treating an automatically Parked Actor as owner-disabled, and treating any wake as permission to resume a deliberately revoked Actor. Preserving a semantic basis rather than a raw residence also keeps retry history and committed prefixes while refusing stale deadlines, certificates, and acknowledgments as executable authority.

## Decision

Accept Candidate A as the sole N4.1 status protocol: process-owned `Serving`/typed `Disabled`/irreversible `Retired`; revocation linearized before direct detach; no economic rollback or custody mutation; cause-scoped explicit revival; current-state reconstruction with exact generation/plan checks and B + 1 eligibility; no stale Park evidence, wake-driven revival, partial revival, or implicit Immutable/System authority. Runtime realization remains open.

## Rejected Alternatives and Tradeoffs

| Candidate | Decision | Evidence-backed reason |
| --- | --- | --- |
| Encode pause as Park | Rejected | Park invalidation would become unauthorized resume and owner intent would masquerade as negative evidence |
| Infer Disabled from missing membership | Rejected | Absence has no typed cause, revival authority, or semantic basis and aliases corruption/cleanup |
| Preserve and reattach raw old residence | Rejected | Deadline, certificate, revision, and round authority may be stale after disabled time |
| Let any ordinary wake resume | Rejected | Source authority is not lifecycle authority and can resurrect retired meaning |
| Reset run/retry state on pause | Rejected | Erases committed-prefix and backoff semantics and enables retry laundering |
| Compensate committed Steps on cancel/update | Rejected | Violates committed-prefix preservation and custody-neutral lifecycle |
| Re-enable Retired | Rejected | Cleanup and replacement generation would gain competing authority |
| Let owner override protocol disable implicitly | Rejected | Expands authority based on status rather than the governing cause contract |
| Reuse one generation across semantic Contract replacement | Rejected | Old cleanup/wake handles can target changed executable meaning |

The accepted tradeoff is a richer process status and complete revival preflight. It buys explicit authority, stale-evidence rejection, and irreversible retirement without a second scheduler or economic unwind.

## Validity

- `Establishes`: Park/status separation, typed reversible causes, revocation linearization, interrupted-Cycle disposition, retry preservation, explicit revival protocol, B + 1 reentry, Immutable/System authority limits, terminal precedence, and irreversible retirement.
- `Does not establish`: Runtime implementation, exact encoding, cleanup topology/throughput, retained-byte collateral, numeric Weight/reserve, or release readiness.
- `Known limitations`: N4.2 must realize old-generation cleanup and replacement coexistence; N4.3 must price retained disabled/retired state; N5.2 must generate every complete control path.
- `Invalidation triggers`: Any ordinary wake revives status, pause erases retry/committed state, stale evidence is reattached, Retired regains service, status expands authority, or old cleanup mutates a replacement.
- `Residual qualitative insight`: Explicit cessation is cheap and safe when serving authority is one process discriminator and revival rebuilds residence from current truth.
