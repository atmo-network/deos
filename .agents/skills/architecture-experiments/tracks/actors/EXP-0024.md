## Decision Question

Should a User Actor reserve run-state hold only while a Cycle exists, or reserve its maximum admitted run-state footprint for the Actor's active installed lifetime?

## Governing Specification

- `Exact sections`: `template/pallets/actors/docs/specification.en.md` → `2.4 Lifecycle, Execution Funding, and Terminal Order`, `4.3 State Holds and Fees`, and `6.4 Weight and Fee Derivation`; `docs/actors-resource-policy.specification.en.md` → `4 Admission and Actual Weight`.
- `Invariant`: State hold is owner-funded, component-exact, fail-closed, and independent of Pipeline Machine and Action fees. System Actors remain exempt. Trigger latching, strict FIFO, Q1, one active plus one deferred Pipeline, custody neutrality, and atomic Step effects do not change.
- `Reopen trigger`: Reopen Specification only if autonomous execution after installation cannot coexist with exact bounded hold authority, or if either reservation horizon requires custody transfer, recurring rent, or class-sensitive scheduling.

## Context and Hypothesis

- `Current architecture`: H0 derives the User Actor hold from current encoded state. Opening inserts `ActorRunStateStore`, then `reconcile_actor_state_hold` acquires the run component from the owner; suspension and each committed Step reconcile actual run bytes, and completion/cancellation releases the component.
- `Reason`: H0 minimizes locked capital but makes autonomous Cycle start depend on owner free balance at Opening and adds hold reconciliation to Opening, progress, suspension, completion, and cancellation. The Trigger and Pipeline fees can be admitted while the subsequent run hold still fails.
- `Hypothesis`: H1 can reserve one conservative maximum run component when an Actor becomes actively installed, eliminate Cycle-local run hold mutations, and allow later autonomous execution after the owner spends all otherwise-free balance, at acceptable lifecycle Weight and capital cost.
- `Materiality`: H1 must remove run-component hold/release mutations from every Cycle transition, preserve component-wise Weight and all semantics, and prove owner-zero-free-balance autonomy. Its permanently locked capital must be explicit and bounded; sub-material Weight reduction without autonomy or state-owner simplification does not justify H1.

## Controls

- `Controlled variables`: Contract, Actor class, schedule, funding, owner balance before reservation, run payload, FIFO position, Q1, database, toolchain, generated-Weight method, runtime resource split, and Task effect.
- `Changed variables`: Run hold target and acquisition/release points only. H0 tracks actual `ActorRunStateStore`; H1 reserves a conservative maximum while the User Actor has installed hot/Contract authority and releases it on deactivation, replacement transition as required, or close.
- `Confounders`: H1's conservative maximum must be derived from admitted runtime types rather than a hand-maintained byte constant. Existing broad `reconcile_actor_state_hold` calls may retain unrelated funding/detector reconciliation even after run mutations disappear.

## Result

H1 reserves the type-derived `805`-byte maximum run footprint whenever User Actor hot authority is installed. At production prices this locks `0.001805` native units per Active User Actor, or `18.05` units at 10,000. The owner-zero-free-balance fixture opens and persists a run because no new owner hold is needed. Full production generation shows User creation RefTime rising `8.4%`, maximum Opening falling `2.0%`, and the mixed execution slope falling `2.2%`; estimated ProofSize and exact I/O are unchanged. The earlier isolated mixed sample was noisy and is superseded by the complete 50×20 generation. Terminal User close still releases all Active hold authority under either horizon.

## Interpretation

H1 moves one bounded cost to installation, where owner authorization and balance admission are explicit, and removes the later owner-balance dependency from autonomous Opening. The `18.05`-unit 10k cost is bounded and small relative to the runtime population commitment. H0 is capital-minimal but can consume a paid useful Trigger and Pipeline admission path only to encounter unavailable run hold. H1 preserves fee, custody, FIFO, Q1, and class-neutral semantics while making installed capacity truthful.

## Decision

Accept H1 active-lifetime maximum run-state hold. Reserve the type-derived maximum when User Active authority is installed, preserve it through Opening/progress/suspension/completion/cancellation, and release it on deactivation or Close. Retain exact holds for all other components.

## Rejected Alternatives and Tradeoffs

| Candidate | Decision | Evidence-backed reason |
| --- | --- | --- |
| Reserve from Actor sovereign custody | Excluded | Violates owner-funded state-hold and custody neutrality |
| Acquire maximum hold lazily at first Trigger | Excluded | Retains autonomous owner-balance dependency and moves the same failure later |
| Charge recurring run rent | Excluded | Actor lifetime has no recurring rent |
| Hand-maintained maximum byte constant | Excluded | Can become stale and under-reserve after type/layout changes |

## Validity

- `Establishes`: H1 owner-balance autonomy, exact `805`-byte/`0.001805`-unit reservation, `18.05`-unit 10k cost, and focused create/Opening Weight tradeoff.
- `Does not establish`: Final release-tree identity or unrelated funding/detector hold optimization; the post-generation Weight/Wasm identities are established.
- `Known limitations`: Final release Wasm and metadata identities remain part of prerelease convergence; complete 50×20 generated Weight now owns production branch authority.
- `Invalidation triggers`: Run layout, hold pricing, lifecycle topology, admission payload, runtime balance semantics, benchmark method, or production Weight changes.
- `Residual qualitative insight`: Reservation horizon couples protocol autonomy to capital efficiency even when storage bytes are unchanged.

## Follow-Up / Next Gradient

```text
Cycle-local run hold → owner-balance liveness dependency
→ active-lifetime maximum reservation → autonomous Opening
→ measure lifecycle Weight and 10k locked capital
→ retain the component-wise Pareto winner
```

- `Eliminated hypotheses`: H0's lower idle capital dominates autonomous liveness; H1 requires stale byte constants; Cycle-local reservation is necessary for exact accounting.
- `Remaining hypotheses`: None for reservation horizon; ordinary production regeneration may correct branch models without reopening H1 semantics.
- `Stop condition`: Accept one reservation horizon only after exact hold accounting, owner-zero-free-balance autonomy, lifecycle rollback, generated Weight, and 10k capital evidence converge.
