## Decision Question

Does the long retry path through Wakeup have complete resource ownership distinct from retained short Ready retry evidence?

## Governing Specification

- `Exact section`: `template/pallets/actors/docs/specification.en.md` §§6.5, 8.2, 9.2 owns retry outcomes, readiness and terminal precedence; `docs/actors-resource-policy.specification.en.md` §§4, 6 owns complete admission/settlement and phases. BACKLOG owns open G6 gates.
- `Invariant`: Temporary Mutable-only retry, one Actor-owned Continuation and existing capped retry/wakeup path; committed prefixes survive.
- `Reopen trigger`: A second retry authority or changed retry semantics requires specification reopening.

## Context and Hypothesis

- `Reason`: Retained short Ready retry accounting does not cover long retry placement through Wakeup.
- `Hypothesis`: Qualified Wakeup placement and subsequent service can account for the long retry path without borrowing short-retry charges.
- `Materiality`: An omitted placement/service owner invalidates complete retry accounting.

## Baseline and Candidates

Selected the existing production-configured System `SwapIn` reference-deviation failure: attempt 1 retains Ready retry, attempt 2 places Wakeup at block 4, block 4 returns through Wakeup without same-block execution, and block 5 performs the terminal third attempt.

## Measurements

The source-bound runtime fixture records four disjoint block-local settlements:

| Phase | Actor Control | Actor effect | Outcome |
| --- | ---: | ---: | --- |
| First failed attempt / Ready retry | `15,253,398,980 / 165,779` | `3,443,678,000 / 19,253` | One continuation, Ready ticket |
| Second failed attempt / long placement | `6,526,601,980 / 90,386` | `3,443,678,000 / 19,253` | Same continuation, Wakeup block 4 |
| Wakeup return | `8,506,170,748 / 95,611` | `0 / 0` | Control-only return; no same-block Task |
| Returned terminal service | `15,650,484,980 / 172,272` | `3,443,678,000 / 19,253` | Third failed attempt, terminal cleanup |

The actor balance is unchanged across all three atomic failed effects. The first two attempts retain one cursor-0 Continuation; Wakeup replaces rather than duplicates the Ready ticket. The block-4 return obeys `N -> N+1`, and terminal cleanup removes process/hot authority.

## Derived Metrics

Long placement differs from short Ready retry and cannot borrow its Control total. Wakeup return owns zero effect; the returned Task effect belongs only to the following block.

## Statistical / Variance Notes

One deterministic native production-runtime fixture; generated Weight settlement is not classified as physical I/O or host timing.

## Result

The selected long retry path has complete disjoint placement, return, resumed-service and terminal ownership.

## Interpretation

Short Ready retry, long-Wakeup placement, Control-only return and later service are distinct owners under one Continuation and one canonical scheduler.

## Decision

Accepted for the selected System `SwapIn` temporary-failure path. No broader Task, retry delay or User-path acceptance follows.

## Rejected Alternatives and Tradeoffs

- `Short Ready substitution`: Rejected because attempt 2 removes the ticket and places Wakeup.
- `Same-block return execution`: Rejected by the causal floor and zero-effect block-4 ledger.
- `Second continuation/scheduler`: Rejected; one cursor-0 Continuation traverses the canonical Ready/Wakeup substrate.

## Validity

Establishes the selected System long-retry resource placement and atomic no-fill behavior. Does not establish other Tasks, delays, User fees or sustained service. Retry, Wakeup, adapter or Weight changes require review.
